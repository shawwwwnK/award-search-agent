# End-to-end diagnostic metric definitions

The baseline settings in the October 8 local harness are `gpt-5.6-luna` for initial intent, clarification receiver/composer, endpoint selection, and gateway discovery; Results starts with `gpt-6-luna`, 16,384 maximum output tokens, a 300-second authoring timeout, 1,050,000 context tokens, 2,048 prompt overhead tokens, and a 922,000 input-token ceiling. Sidebar settings are editable, so each run should retain its actual values. The Results counting endpoint measures each complete authoring request before generation and a correction may make a second request. See `apps/clarification_harness.py` and `src/award_agent/harness/pipeline.py`.

For every case, record elapsed wall time from input through final Results delivery, plus stage times where measured. The harness intent telemetry aggregates calls, input/output/total tokens, and model-call latency by event; private local call traces may contain exact payloads and full responses, but the aggregate export omits cached-token detail. Planning diagnostics report elapsed time and M2A selector *total* tokens only; the saved M2B gateway invocation retains usage and trace latency. Direct airport endpoints and same-market gateway skips can legitimately have zero planning model calls. Provider results retain Seats.aero and gfly request, attempt, page/detail, row, byte and elapsed-time receipts. Ranking is deterministic; the current pipeline has no dedicated ranking duration receipt. Results attempts retain writer usage, response, and generation latency, while input-token count receipts support request-size assessment.

The applicable [official OpenAI Docs rates for GPT-5.6 Luna](https://developers.openai.com/api/docs/models/gpt-5.6-luna) and [GPT-6 Luna](https://developers.openai.com/api/docs/models/gpt-6-luna) are pinned in `pricing-basis.json`. Estimate model generation cost per request, applying long-context rates only when **that request** exceeds 272,000 input tokens. If only aggregate input/output totals survive, label an uncached estimate as approximate; do not derive a long-context rate from a case or stage total. Raw response usage can be consulted for cached-input detail when present. Cache-write class visibility is not established by the normalized receipts. The Results input-token counting endpoint, provider billing, and failed calls lacking response usage are outside any quoted generation estimate.

The offline `summarize.py` uses raw `input_tokens_details.cached_tokens` and `input_tokens_details.cache_write_tokens` when present. Its uncached class is `input_tokens - cached_tokens - cache_write_tokens`; the two cache classes must not also be charged at the ordinary input rate. A raw response lacking a cache detail field currently defaults that field to zero, so its resulting estimate needs a missing-detail caveat. Pricing is keyed by the requested model; compare the response's `model` with it before treating a campaign estimate as verified. Duplicate captured SDK wrappers and copied attempts must be reconciled by response ID before summing campaign charges.

These metrics describe the observed diagnostic executions and their saved artifacts. They do not establish broad model context fit, provider reliability, semantic answer correctness, owner qualification, or an adopted end-to-end golden set.
