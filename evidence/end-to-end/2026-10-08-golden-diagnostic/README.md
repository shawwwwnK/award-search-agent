# Intent golden cases through Results M2: development diagnostic

The source is the active 19-case intent behavior corpus at
`evals/intent/one_way_award_behavior_cases_v1.yaml`. `cases.json` selects six
requests. It preserves each original fixture, records the executed text/context,
and labels the two date adaptations. The original oracle is not automatically
applied to adapted inputs. Scripted clarification answers are separately
labeled diagnostic continuations from facts in the original fixture; the first
model interpretation and its blocker remain visible.

The owner requested a separate **early-2027** batch to use future travel dates
for real live acquisition. Its six derivatives are
in `cases-early-2027.json`, all with October 8, 2026 as the reference date and
explicit expected departure windows. It replaces the New York–Lisbon relative
weekend with the home-airport/business case. Run any case with
`--campaign early-2027 --provider-profile compact`; artifacts go under
`early-2027/runs/CASE_ID/`. The original runs remain intact. These are revised
diagnostic inputs, not unchanged golden cases.

Run one case with:

```bash
.venv/bin/python evidence/end-to-end/2026-10-08-golden-diagnostic/run.py --case ready_whole_month
```

Use `--preflight` to validate a case and local settings without live calls. If a
stage fails after saving its output, use `--resume-from` with that run directory;
the continuation is saved under `continuation-N` and does not repeat completed
intent or planning model calls. A blocked original case resumes through the
same clarification controller and answer interpreter as the local harness.

For a supplemental small acquisition on the same saved compiled plan, add
`--provider-profile compact --resume-from RUN_DIR`. The explicit
`provider-compact.json` policy changes the bound to three award requests and one
direct cash request, with partial coverage retained in the provider result.
This is a distinct diagnostic execution policy, not a comparable full-policy
replay or a claim of complete provider coverage. A policy change always triggers
new provider acquisition; a same-policy resume can reuse a saved provider result
and tape after a later-stage failure.
The three-request/three-page award budget can be exhausted before detail calls,
so zero complete journeys under this profile can reflect limited acquisition
rather than absent award inventory. Any standard-policy exception must be
recorded in that run's `summary.json` and `provider-bundle.json`.

The runner writes raw per-call SDK requests/responses, exact intent adapter
traces, typed stage JSON, provider tape and bodies, Results artifact and answer,
stage wall times and partial failures under ignored `runs/CASE_ID/`. These are
private local traces; SDK credentials are excluded. Each Results artifact is
replayed and checked against the saved Markdown. Provider tape replay is also
compared with the saved provider result and the result of that comparison is
reported, including any mismatch. `summary.json` separates live pipeline stage
time from verification time. Model usage is exact where SDK responses report it;
missing usage is unknown, not zero. `/responses/input_tokens` measurement calls
are separately labeled and excluded from generation totals.

Provider bodies/tape are retained after a provider stage returns. If an attempt
is interrupted or errors inside acquisition, the harness temporary evidence
directory is cleaned up and that attempt has no complete provider tape. Its
summary and completed earlier stage records still show where it stopped.

The October 8 Results run uses the explicit `declared.config.json` settings
(gpt-6-luna, 32,768 output tokens, 600-second timeout and saved authoring
guidance). Intent, airport selection, gateway discovery and clarification use
gpt-5.6-luna. Provider capability, FX and catalog paths come from
`HarnessSettings`; settings hashes are retained with each run. Results quality,
semantic truth and provider coverage require human review beyond exact replay.

Early attempts made with the first runner revision recorded duplicate SDK
wrapper entries for a single model call. After those processes finish, run
`reconcile.py` to preserve each original index and remove duplicated entries
from the accounting index without another paid call. See `metrics-notes.md` and
`pricing-basis.json` for the cost basis and its limits.
Pass `--campaign early-2027` to `reconcile.py` and `summarize.py` for the new
batch after its runs finish.

The parent reviewer index is generated by `verify_and_report.py` after both usage
summaries exist. It independently replays every retained Results artifact and
checks its projection against the saved Ranking export, then links each revised
input, initial interpretation, continuation, final answer and stage trace.
Its live latency sums measured stages along the retained continuation chain;
permission gaps and offline replay time are excluded rather than silently added.
See `report.md` and `report.json` when campaign verification is complete.

Final standard-budget contrasts use `continuation-3` for the January 8 typo and
January 15 mixed request. Their `continuation-2` predecessors incorrectly reused
compact policy under a standard label; dispositions preserve that runner defect.
Actual frozen policy receipts determine valid profile comparisons.

Exact replay has a cross-process finding-order defect in an annotated compact
comparison. `replay-order-probe.json` records separate hash-seed probes; the verifier
reports this receipt failure without changing runtime code or saved artifacts.
